## 三、共通契約與資料字典

- 統一Renewal命名、小寫路徑、JSON camelCase、DTO直接回傳，不序列化JPA Entity。
- JSON日期YYYY-MM-DD；時間HH:mm:ss（原出席卡片維持HH:mm）；日期時間YYYY-MM-DDTHH:mm:ss，以Asia/Taipei解讀，不誤轉UTC。DATETIME既有毫秒可於F3額外完整保留，詳見F4。
- 教練由登入Session取得，不能由Request coachId決定授權；accountId不等於coachId。每支先驗證登入、方案存在與membercourse.coachid；所有方案不擴權。
- 無資料集合[]；無選填值null；未登入401、越權403、資源不存在404。停用會員仍可查歷史、新增跟進與更正既有紀錄；新購課／續約409。
- Path ID為正整數。錯誤參數／未知Query值400。姓名部分比對需參數化，%/_等當字面搜尋，不串接原始SQL。字串trim依Java strip/JS trim一致政策；備註上限以UTF-16單位，保留內部換行且純文字顯示。
- R1／F1每頁固定10，B2固定5；page為1起算，size可省略，傳入只接受對應固定值（其他400）。頁碼非整數或<1回400。總頁數無資料為0，但page回1；超頁回最後有效頁，回傳實際page。totalElements為全部篩選結果，不是items.length。分頁以資料庫穩定排序後取得。
- 每次請求固定一個asOfDateTime台北時間，衍生asOfDate；不提供前端任意改基準日參數。同次R1統計／列表／分頁須使用一致資料快照（如SQL Server SNAPSHOT或等效一致查詢；隔離設定需實作，不以多次各自GET冒稱同快照）。

| 類別 | 代碼 | 中文 |
|---|---|---|
| scope | TRACKING／ALL_PLANS | 全部待追蹤／所有方案 |
| category | ALL／HIGH_PRIORITY／UPCOMING／LONG_ABSENT／COMPLETED | 全部／優先聯繫／堂數將盡／久未到課／已用完 |
| 跟進查詢 | ALL／NOT_CONTACTED／NO_RESPONSE／CONSIDERING／AGREED／DECLINED | 全部／未聯繫／尚未取得回應／考慮中／同意續約／無意願 |
| 新增／修改結果 | NO_RESPONSE／CONSIDERING／AGREED／DECLINED | 四種結果，不能寫ALL或NOT_CONTACTED |
| 聯絡方式 | PHONE／MESSAGE／IN_PERSON／OTHER | 電話／訊息／當面／其他 |
| 付款 | cash／transfer／card | 現金／轉帳／信用卡，僅這三個小寫值 |
| 會員 | active／inactive | 啟用／停用 |
| 方案 | active／usedup | 有剩堂／已用完 |

NO_RESPONSE、MESSAGE為本次API統一代碼，長度符合現有NVARCHAR(20)。舊LINE值不無聲改寫：可保留原值並顯示「訊息（LINE）」；未知歷史回原代碼、由前端未知狀態顯示，不能當NOT_CONTACTED。最新歷史是NULL／未知時followupStatus保留NULL／原值；ALL可查，NOT_CONTACTED僅限完全無FollowUp。

### A1～A3參數驗證政策

- A1僅接受一個必填date；未知Query參數名稱、重複參數均回400。
- A2與A3不接受任何Query參數，傳入即回400。
- A2與A3的bookingId須為正整數；0或負數回400，合法但不存在的ID回404。
- date沿用Spring的LocalDate與ISO日期轉換；缺漏、空白、無法解析或不存在的日期回400。不新增全域日期解析器。
- bookingId非數字或超出Java Integer範圍回400，沿用既有型別轉換及GlobalExceptionHandler。
- 上述是Attendance Controller的局部契約，不自動套用到其他組員的API；身分／權限驗證仍維持既有流程，未登入可能先由攔截器拒絕。

### 出席規則的必要增補（優先於舊段落）

A1～A3下節保留舊契約；最新生命週期要求扣堂／補堂時同交易同步status：remaining=0→usedup，>0→active，不改total。剩堂超total或負數屬異常，不截斷掩蓋。會員停用不刪資料、不清堂、不改方案狀態；既有出席更正仍可按原權限處理，不能一律以會員inactive拒絕。Booking指向哪筆就扣補哪筆；不要把續約新方案帶入舊Booking。

原出席A2的本方案近期歷史保留；R1/R2同組最後出席另設courseActivity，不能把兩種範圍混成同一欄。Booking BOOKED/CANCELLED與組員小寫值需統一或轉換，不能漏擋取消。

## 四、A1：取得指定日期出席工作台

```
GET /api/coach/attendance?date=YYYY-MM-DD
```

範例

```
GET /api/coach/attendance?date=2026-09-27
```

### 用途

一次取得指定日期的統計與課程卡片，供日期切換後重新載入整頁資料。

### Query

| 參數 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `date` | 日期字串 | 是 | 格式 `YYYY-MM-DD` |

### 查詢規則

- 限定目前教練負責的 MemberCourse。
- Booking 關聯排課、MemberCourse、會員、課程與 Attendance。
- 沒有 Attendance 時，卡片顯示 `PENDING`。
- GET 不因查詢而自動新增 Attendance。
- 卡片依 `startTime`、`bookingId` 升冪排列。
- 取消預約仍顯示卡片，但前端呈現灰色且不可操作。

### 統計規則

- `totalClasses` 是回傳的預約卡片總數，包含取消卡片。
- 取消卡片只計入 `cancelled`。
- 取消卡片不重複計入其他出席狀態。
- `present＋pending＋leave＋absent＋cancelled＝totalClasses`。

### 200 Response

```json
{
  "date": "2026-09-27",
  "summary": {
    "totalClasses": 1,
    "present": 0,
    "pending": 1,
    "leave": 0,
    "absent": 0,
    "cancelled": 0
  },
  "classes": [
    {
      "bookingId": 7,
      "scheduleId": 8,
      "startTime": "09:00",
      "endTime": "10:00",
      "memberCourseId": 1,
      "memberId": 1,
      "memberName": "王小美",
      "avatarUrl": "/images/members/member01.jpg",
      "courseName": "私人教練一對一",
      "remainingSessions": 2,
      "bookingStatus": "BOOKED",
      "attendanceStatus": "PENDING"
    }
  ]
}
```

沒有預約時回傳 `200`、零統計與 `classes: []`。

`BOOKED`、`CANCELLED` 的實際合法值須與組員 Booking 規格一致。

## 六、A3：更新出席

```
PUT /api/coach/attendance/{bookingId}
```

範例：

```
PUT /api/coach/attendance/7
```

### Request 欄位

| 欄位 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `status` | string | 是 | PRESENT、LEAVE、ABSENT |
| `workoutFocus` | string／null | 否 | 訓練重點 |
| `note` | string／null | 否 | 備註 |
| `inBody` | object／null | 否 | 身體數據 |

`PENDING` 是初始狀態，目前不接受透過此 PUT 重設。

### PRESENT Request

```json
{
  "status": "PRESENT",
  "workoutFocus": "重量訓練",
  "note": "深蹲60kg 3組，狀態良好",
  "inBody": {
    "weight": 59.5,
    "bodyFatPct": 28.2,
    "muscleMass": 23.5
  }
}
```

### LEAVE Request

```json
{
  "status": "LEAVE",
  "workoutFocus": null,
  "note": "會員臨時有事請假",
  "inBody": null
}
```

### ABSENT Request

```json
{
  "status": "ABSENT",
  "workoutFocus": null,
  "note": "會員未到場且未事先請假",
  "inBody": null
}
```

### 堂數規則

| 原狀態 | 新狀態 | 剩餘堂數變化 |
| --- | --- | --- |
| PENDING／LEAVE／ABSENT | PRESENT | −1 |
| PRESENT | LEAVE／ABSENT | ＋1 |
| PRESENT | PRESENT | 0 |
| LEAVE | ABSENT | 0 |
| ABSENT | LEAVE | 0 |
| 相同狀態 | 相同狀態 | 0 |

相同狀態不改堂數，但可更新備註與訓練重點。

### Service 流程

1. 確認 Booking 存在。
2. 確認目前教練有操作權限。
3. 確認 Booking 未取消。
4. 驗證 Request。
5. 取得舊狀態並比較新狀態。
6. 呼叫 MemberCourseService 扣堂或補回。
7. 更新 Attendance。
8. 依規則處理 InBody。
9. 儲存成功後回傳最新明細。

### 交易規則

由 `AttendanceService` 使用 `@Transactional`，讓下列修改在同一交易中完成：

- Attendance。
- MemberCourse 的剩餘堂數。
- 本次 InBodyRecord。

任何必要操作失敗，整次修改回復。

資料庫維持 `attendance.bookingid` 唯一限制，並須處理並行更新，避免重複扣堂。

### workoutFocus 與 note

- workoutFocus 選填；PRESENT 可填或不填。
- LEAVE／ABSENT 前端原則上傳 null。
- 後端不因 status 自動清空 workoutFocus，而依 Request 傳入值更新。
- note 選填，依 Request 更新。部分欄位省略的行為須與目前 DTO 對齊，不推定為 PATCH 語意。

### InBody 最終規則

InBody為選填，不要求每次出席都提供量測。以下量測內容驗證適用於新狀態為PRESENT；LEAVE／ABSENT的處理優先依最後一列。

| 情境 | 規則 |
| --- | --- |
| PRESENT，inBody為null或省略 | 本次未提供量測，不新增、不刪除、不修改既有InBody |
| PRESENT，weight／bodyFatPct／muscleMass三值全部null（含空物件或欄位省略後皆為null） | 本次未提供量測，不新增、不刪除、不修改既有InBody |
| PRESENT，完整有效inBody，尚無紀錄 | INSERT，關聯本次Attendance |
| PRESENT，完整有效inBody，已有紀錄 | UPDATE原紀錄，不新增第二筆 |
| PRESENT，任一欄有數值但未填完整三欄 | 400，整次交易回滾 |
| PRESENT，完整三欄但任一數值小於或等於0 | 400，整次交易回滾 |
| PRESENT改LEAVE／ABSENT | 刪除該Attendance的InBody，依原出席規則補回一堂 |
| 新狀態為LEAVE／ABSENT | 忽略傳入InBody的量測內容、不新增或更新量測，刪除既有關聯量測；是否補堂仍取決於舊狀態，原本非PRESENT不額外補堂 |

- 有提供量測時，weight、bodyFatPct、muscleMass必須三欄完整且皆大於0，並符合既有數值範圍及小數位驗證；不將部分欄位自動補0。
- 同一Attendance最多一筆InBody；完整object是整筆更新，不是單欄修補。
- 「未提供量測」只表示不變更InBody；仍處理出席狀態、扣補堂、訓練內容及備註，不將整個PUT視為不操作。
- 沒有量測時前端建議傳inBody:null；三值全null亦合法。既有量測不會因此清空。
- 非出席忽略量測內容，不代表接受格式錯誤的JSON或無法轉換成DTO的型別；原有JSON解析錯誤處理維持不變。
- B2查詢仍排除資料庫中三值全部null的無效歷史量測；A3不建立空量測與B2歷史篩選是不同規則，B2不變。

### checkInTime／updateTime 最終規則

| 狀態變更 | checkInTime |
| --- | --- |
| 第一次變成 PRESENT | 本次實際操作時間 |
| PRESENT → PRESENT | 保留原 checkInTime |
| PRESENT → LEAVE／ABSENT | null |
| LEAVE／ABSENT → PRESENT | 重新記錄本次操作時間 |
- A3使用Asia/Taipei取得實際操作時間，供updateTime及需要新設的checkInTime使用。InBody的recordDate取該次Booking關聯的ClassSchedule.classdate，代表上課當天的量測日期，允許事後補登或更正，不使用補登操作日。
- 不修改SQL Server DATETIME／DATE型別、不批次轉換舊資料，JSON沿用不含offset的當地日期時間格式；不變更JVM／Jackson全域時區。
- 每次成功 PUT，updateTime 更新為本次操作時間。
- 操作失敗或 rollback，不保留此次時間更新。
- 原排課日期與時間不變；補登時間不是原上課時間。
- DB 欄位沿用 updatetime，Java／JSON 命名若使用則為 updateTime。本版既有 Detail JSON 未約定回傳 updateTime，不擅自增加欄位。

### 200 Response

回傳與 API 2 相同的 `AttendanceDetailResponse`，包含最新狀態與剩餘堂數。

前端成功後重新取得 API 1，更新統計與卡片，不自行假設堂數減一。

## 七、共用分類與日期計算（R1/R2）

1. 方案集合限目前教練，保留正常、歷史、usedup、已續約與停用會員的可見歷史，不因會員停用隱藏或刪除。
2. hasRenewed=存在renewal.membercourseid=本方案ID且指向實際新方案的成功紀錄。資料表沒有成功狀態欄，提交交易成功的現存紀錄即為成功，不能靠AGREED推定。
3. HIGH_PRIORITY=剩1～5且!hasRenewed；UPCOMING=剩6～10且!hasRenewed；COMPLETED=剩0且!hasRenewed。
4. LONG_ABSENT=本方案剩堂>0且courseActivity.daysSinceBaseline>=14。與其他分類可重疊，不設分類排序優先級。DECLINED不取消任何分類。兩scope用同一tags。
5. TRACKING=至少一tag；ALL_PLANS=所有授權方案。特定category在兩scope結果相同。新方案獨立算堂數與hasRenewed、不繼承FollowUp。

7. 同組沒有有效PRESENT，取同組purchaseDate<=asOfDate的最早日為baseline；不是這筆方案購買日。baselineType=FIRST_PURCHASE，lastPresentDate/daysSinceLastPresent=null。若有出席，baselineType=LAST_PRESENT且baselineDate=lastPresentDate。新購課不重設天數；不同教練／課程不混算。
8. daysSinceBaseline按日曆日期差；同組沒有合法基準則baselineDate/daysSinceBaseline=null，不判久未到課並回報資料品質問題，不虛構0天。
9. 用outgoingRenewals[]回全部新方案，不用單一newMemberCourseId覆蓋多筆。每筆包含renewalId/newMemberCourseId/courseId/courseName/purchaseDate/renewalDate，順序renewalDate DESC、renewalId DESC。

### 本期範圍

本期不實作持久化提交去重，不新增api_submission資料表，也不為提交編號修改FollowUp／Renewal資料表。F2、P2保留現有SubmissionGuardService，以單一後端程序內的記憶體保存短期提交狀態與成功結果；本期驗收以本節有限範圍為準，不再要求跨程序重啟後仍能重播原結果。

此為API契約的範圍調整，不表示完全取消後端去重，也不表示前端防連點已實作完成。

### Header與作用域

- F2／P2仍須傳入Idempotency-Key，格式為UUID；缺漏、格式不合法或重複Header回400。
- 每次有意新增產生新key；同一次操作在保護有效期間內重送，沿用原key及相同內容。不同key視為不同操作，不能僅憑會員、課程、金額或備註相同就拒絕合法新增。
- 作用域為登入帳號＋HTTP方法＋後端組合的標準資源路徑＋key。後端綁定正規化Request的SHA-256摘要，不能跨使用者或方案共用成功Response。
- 每次請求（含重送）仍驗證登入與方案授權；提交編號不取代身分及權限驗證。

### 暫存有效時的行為

| 情況 | 回應與處理 |
|---|---|
| 新key、合法內容且容量足夠 | 執行一次業務交易，成功201後保存結果 |
| 同作用域、同key、同內容，已完成 | 回第一次成功的HTTP狀態與JSON，不再INSERT |
| 同作用域、同key、不同正規化內容 | 409，不新增資料 |
| 同key同內容仍處理中 | 409；前端不自動重試POST |
| 提交結果不明 | 409，提示先查詢紀錄，不直接再次執行 |
| 暫存容量已滿 | 409，拒絕新的提交，不淘汰尚在有效期的成功結果來放行新增 |

- 已完成及結果不明的項目，自各自完成／標記結果不明起保留30分鐘，於後續請求時清除過期項目；處理中項目不因這個時限直接移除。
- 總容量最多1,000筆，包含處理中、已完成及結果不明；同程序內須同步管理項目，避免同key同時請求各自新增。
- 必須等資料庫交易成功提交，才將記憶體項目標為成功；不能在交易尚未提交時就對重送回傳成功。
- 業務失敗應回滾，不保留半套成功結果。交易系統例外且結果無法確認時標為結果不明，要求先查詢。
- 原成功結果重播不是新的購課。若第一次已成功、會員後來停用，登入與方案授權仍有效且暫存命中時，可回既有結果；新的購課操作仍須驗證會員active。

### 明確限制

- 記憶體暫存不屬於SQL Server交易，也不與業務資料形成持久化的原子提交。
- 後端重啟或程序崩潰會遺失暫存；保留期限過後，舊key也可能被當成新操作。資料庫已提交、但成功結果尚未記入記憶體前若程序中斷，也可能無法辨認先前提交。
- 多個後端執行個體不共用記憶體，因此不保證跨執行個體去重。此方案僅適用目前單一後端執行個體的交付範圍。
- 上述情境中，即使沿用原key也可能重複新增。不得宣稱永久去重、跨重啟安全重試或任何情況下只執行一次。

### 前端配合規則（前端串接時驗收）

1. 送出後立即鎖定按鈕，防止重複點擊；新增POST不自動重試。
2. 同一次送出只產生一個key，不在每次網路重試時另產生key。
3. 發生逾時、網路中斷或結果不明時，顯示「結果尚未確認，請先查詢紀錄」，不可直接提示新增失敗並鼓勵再次送出。
4. 重新查詢F1跟進列表，或R2續約關聯與新方案，讓使用者確認是否已成功；這是人工確認流程，不是持久化去重的替代保證。
5. 確認前次結果後，若使用者確實要進行另一次新增，才產生新key。查詢紀錄不等於必須額外實作「看完才能解鎖」的新按鈕或後端鎖定機制。

## 十六、MemberCourse與管理端首次購課介接

### 共用查詢建議（M1/M2，正式路徑需與組員對齊）

```http
GET /api/member-courses/{memberCourseId}
GET /api/member-courses?memberId=1&usableOnly=false
```

M1回200包含memberCourseId/memberId/memberName/courseId/courseName/coachId/coachName/purchaseDate/totalSessions/remainingSessions/status，型別同R2。不存在404、越權403。

M2回相同結構陣列，無結果[]，purchaseDate DESC/ID DESC，usableOnly=true只active且remaining>0。管理員可指定會員，教練只查負責方案；會員只查自己（指定他人403）。管理員與教練須指定正整數memberId，無此會員404；會員可省略由Session取得。這是共用查詢提案，非預約組原GET /members/courses替代版，不改其既有小寫JSON。

### 首次／一般購課的共通規則

- 首次購課先有會員，建立全新MemberCourse，total=remaining=本次堂數、status=active、有效日期、合法coachcourse；同會員同課同教練可多筆。不建立假Renewal，不重設舊方案。
- 管理員可處理跨教練購課；教練續約P2只固定自己。一般再購但無明確Renewal關聯，不推定來源已續約。
- 停用會員不能新購課，保存歷史，不把membercourse.status改inactive；身份由後端驗證。
- 最新SQL MemberCourse無金額或付款欄，Renewal要求來源非空，不能用來源=新ID假造首購Renewal。若管理端需保存首購金額，須確認訂單／交易模型。
- 已知組員可能已有AdminPurchaseReqDTO、AdminPurchaseCourse及Controller，但本次未收到程式，故**不另強制定稿POST /api/member-courses**。先對齊實際路徑／DTO及兩邊Entity，避免重複購課入口。舊API10標為介接待確認，不刪掉首次購課需求。
- 出席扣補堂、新購建立屬共用MemberCourseService；續約不再呼叫addSessions；可共用建立方法，但不可先前端呼叫首購再呼P2新增兩份。
- 不提供任意PATCH堂數、DELETE、退款、換課、到期功能；明確不同課加購是新購，不是換舊課。

## 十七、錯誤、資料安全與交易

| HTTP | 規則 |
|---|---|
| 200 | GET、出席PUT、跟進PUT成功 |
| 201 | 新增跟進、續約成功；有效記憶體暫存命中時重播原成功狀態 |
| 400 | JSON/日期/列舉/INT範圍/未知寫入欄位/必填/UTF-16長度錯誤 |
| 401 | 未登入或失效 |
| 403 | 非教練或其他教練方案；不是用Request ID取得權限 |
| 404 | Booking/方案/FollowUp/課程不存在，FollowUp與路徑方案不匹配 |
| 409 | 取消預約、堂數不足、停用會員不能購課、資源失效、去重內容衝突／處理中／結果不明／暫存容量已滿、編輯時間原值已變 |
| 500 | 非預期系統錯誤或需修復的資料完整性錯誤 |

```json
{"timestamp":"2026-10-18T17:00:00","status":409,"error":"Conflict","message":"此會員已停用，請先恢復會員後再辦理續約"}
```

延續GlobalExceptionHandler timestamp/status/error/message，不另換code格式。前端按HTTP與操作情境顯示，必要欄位錯誤可由message說明；內部SQL/stacktrace不外洩。空資料不是查詢失敗，不吞exception回0。

GET不建立出席、不更新狀態、不修復歷史。Attendance交易涵蓋Attendance＋剩堂與方案status＋InBody；P2資料庫交易涵蓋新方案＋Renewal；F2資料庫交易涵蓋新增FollowUp。成功結果序列化在業務交易內完成，成功暫存於資料庫提交後寫入程序記憶體，兩者不構成持久化原子交易，限制見第十五節；F4僅原筆可改欄。內部建立方法不獨立REQUIRES_NEW先提交。

會員停用／恢復是更新帳號或會員狀態，不DELETE購課與歷史。SQL某些關聯有ON DELETE CASCADE，JPA另有可能的CascadeType.REMOVE；這些不是軟停用保護。需組員檢查停用Service／@SQLDelete／Entity級聯及查詢過濾，不僅修改你自己的Entity就宣稱可防所有刪除。
